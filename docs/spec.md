# 샛길 기능·요구사항 명세 v3

2026-11-03

**구현** = 11/10 제출까지 실제 동작 · **목업** = 화면만 · **발표만** = 자료에서 언급 · **스트레치** = 11/7 이후 여유 시 · ⚠️ = 추천값, 팀 확인 필요

이 문서는 코드 생성의 기준이다. 여기 없는 기능은 만들지 않는다. "적절히", "등" 같은 표현은 쓰지 않고, 모든 기능은 입력·처리·출력·예외·테스트 기준을 가진다.

## 개요

**샛길은 출퇴근 중 '걷는 구간'을 바꿔, 결심 없이 자연을 지나가게 하는 웹앱이다.** v3의 변경은 셋이다: AI의 자리를 "후보 중 선택"으로 확정했고, 취향 필터와 피드백 가중치를 넣었고, 사진 계절 태그를 비전 AI로 바꿨다.

| 항목 | 내용 |
| --- | --- |
| 정의 | 결심 없이, 자연을 지나는 하루 |
| 성격 | 지도 앱 대체 ❌ · 알림 오면 여유 있을 때 여는 앱 |
| 슬로건 | 걸음 대신 **계절**을 센다 |
| 샛길의 정의 | 출퇴근 **경로 전체**가 아니라 **걷는 구간**을 바꾸는 것. 탑승 횟수는 늘리지 않는다 |
| 교통수단 가정 | 대도시 통근의 다수는 대중교통이고 도보 전체 통근은 소수다. 샛길은 **대중교통 양 끝의 도보 구간**을 기본 대상으로 하고, 도보 통근은 전체 구간, 자동차 통근은 도착 후 구간만 다룬다 |
| 형태 | 웹앱 (모바일 우선) |
| 탭 | 홈 · 경로 · 기록 · 마이 |
| 계정 | 이메일·비밀번호 가입(닉네임 포함, 인증 메일 없음) · 둘러보기. Supabase Auth. 소셜 로그인은 2차 |
| 지역 | 대구 우선. 서울 전환은 스트레치 (코드는 city 파라미터로 분리) |
| 데모 동선 | ⚠️ 대구 2호선 수성구청역→반월당역 구간 퇴근 18:10, 한 정거장 먼저 내리기. 도보 대안 1개, 서울 1개(스트레치) |

## 길찾기에서 AI의 자리

**경유지 추리기는 규칙, 경로는 지도 API, 점수는 규칙, 오늘의 하나를 고르는 것은 AI.** AI는 실제 경로의 숫자(+분 · 녹지 % · 이벤트)가 나온 뒤에만 개입한다.

```
자연 지점 테이블 (대구 200~300개)
  ↓ 규칙 ① 기준선 600m 버퍼 안                        → ~12개  (PostGIS)
  ↓ 규칙 ② 직선 우회량 dist(A,W)+dist(W,B)−dist(A,B) ≤ 1km → ~6개   (산수)
  ↓ 규칙 ③ 취향 필터 (태그 · 우회 상한)                 → ~4개
  ↓ 그래도 6개 초과면 우회량 적은 순 상위 6개
지도 API 호출 ≤ 6번 (경유지 1개씩, 하천은 진입·진출 쌍을 1개로)
  ↓ 규칙 ④ 녹지 % · 이벤트 점수 · 피드백 가중치 · 상한 → 후보 ≤ 3개
AI 1회: 후보 ≤ 3개 + 오늘 맥락 → 선택 + 이유 + 문장
```

왜 추리기를 AI로 하지 않는가: 실제 경로 숫자를 모르는 상태에서 고르면 조건 미달(+25분) 추천이 나오고, "왜 이 길인지" 설명이 안 된다. 후보 지점이 늘어나도 규칙 ①②로 API 호출 수는 6 이하로 고정된다.

## IA

```
앱 실행 → 로그인 / 가입 / 둘러보기 → (처음이면) 출퇴근 설정(교통수단·취향 포함) → 홈

홈                   경로                     기록              마이
├ 오늘의 카드 (1장)     ├ 경로 상세 (추천 1 + 이 길로)   ├ 남기기 (비전 태그)  ├ 출퇴근 정보 수정
│  ├ 취향 칩 3개        ├ 다른 길 보기 (≤3 + 최단)       ├ 모아보기 (장소별)   ├ 취향 설정
│  └ 다른 길 보기       ├ 걷는 중 → 별점             └ 장소 기록 (켜켜)    ├ 알림 설정
├ 오늘의 계절           └ 주변 자연 (발표만)                                └ 지역 (스트레치)
└ 지역 토글 (스트레치)
```

홈은 카드 1장이다. "지금 시간대"에 맞는 카드 하나(오전이면 출근길, 오후면 퇴근길)만 보이고, 출근길·퇴근길 카드를 나란히 두지 않는다. 매일 여러 개 중 고르는 것은 결심 비용이다.

## 사용자 플로우

1. **로그인** — 이메일·비밀번호 (가입 시 닉네임). 둘러보기는 계정 없이 데모 동선 열람
2. **출퇴근 설정** — 출발 · 도착 · 출퇴근 시각 · 교통수단 · 기본 취향. 대중교통이면 노선·정류장 확인 (처음 1회)
3. **알림** → 홈 카드 (행동 유형: 돌아가기 · 먼저 내리기 · 걸어가서 타기 · 늦추기 · 고개 돌리기 · 도착 후)
4. 카드 아래 **취향 칩** (짧게 · 제대로 · 노을) — 그날만 바꾸고 싶을 때. 안 누르면 기본 취향
5. **"이 길로"** → 경로 상세 (추천 1개). 비교가 필요하면 "다른 길 보기"
6. **걷는 중** — 자연 구간 도착 시 방향 포함 안내 → 도착 시 **별점 1~5 한 번** → (선택) 사진 남기기
7. **모아보기** — 장소별로 계절 기록이 쌓임

대중교통 퇴근의 걷는 구간은 앞·뒤 두 토막이고, 정거장을 1~3개 건너뛰어 걷는 구간을 늘릴 수 있다 (11/6 결정 #51). 샛길은 이 중 하나만 바꾼다.

| 패턴 | 바꾸는 구간 | 예시 |
| --- | --- | --- |
| 앞 도보 바꾸기 | 회사 → 정류장 | 사무실 → 경상감영공원 지나 중앙로역 |
| **1~3 정거장 먼저 내리기** | 1~3 정거장 전 → 집 | 범어역 대신 수성구청역에서 내려 신천 따라 +12분 |
| **1~3 정거장 걸어가서 타기** | 회사 → 1~3 정거장 뒤 | 회사 앞 대신 두 정거장 걸어가 공원 옆 정류장에서 타기 |
| 뒤 도보 바꾸기 | 정류장 → 집 | 출구 반대편으로 나가 공원 통과 |
| 지원 안 함 | 중간 하차 후 재탑승 | 환승 대기·요금·결심이 생겨 원리와 어긋남 |

## 핵심 기능 상세

### F-01 로그인 · 가입

- **가입** 이메일 · 비밀번호 · 닉네임. 프론트가 Supabase `signUp`, 닉네임은 `options.data.nickname`. 인증 메일 OFF
- **로그인** 프론트가 Supabase `signInWithPassword` → access token
- **서버** `Authorization: Bearer {token}`을 Supabase JWKS로 검증. 최초 요청 시 `sub`로 User 생성, 닉네임은 `user_metadata.nickname`, 없으면 "샛길러"
- **둘러보기** 토큰 없음. 데모 동선 조회만 허용, 저장·기록·피드백은 로그인 필요
- **데모 계정** `scripts/seed_demo.py`로 생성. 심사 제출 시 이메일·비밀번호 동봉
- **범위 밖** 소셜 로그인, 비밀번호 재설정, 이메일 변경
- **테스트 기준** 만료 토큰 401 · 서명 불일치 401 · 토큰 없음 401 · 정상 토큰 → 200 + User 생성 · 두 번째 호출 같은 User · 닉네임 없는 토큰 → "샛길러"

### F-02 출퇴근 설정

- **입력** 출발 좌표 · 도착 좌표 · 출근 시각 · 퇴근 시각 · 교통수단(`walk` / `transit` / `car`) · 기본 취향(`short` / `full` / `sunset`, 기본 `full`)
- **처리** `transit`이면 대중교통 API(⚠️ ODsay)로 노선·정류장 목록 조회 → 사용자가 확인. 데모 동선은 Station 테이블의 2호선 정류장으로 API 없이 동작. 저장 뒤 프론트가 `POST /commutes/{id}/routes`를 호출해 동기로 계산한다(10초). 데모 동선은 시드에서 미리 계산한다
- **저장** 출발·도착 좌표(POINT) · 동 단위 area · 시각 · 교통수단 · 노선 · 정류장 ID · 취향. 좌표는 경로 계산에만 쓰고 본인 응답 외에는 내보내지 않는다 (11/3: 경로선 저장과 재계산을 위해 저장으로 변경)
- **탑승 계획 여러 개 (#88)** 평소 타는 노선이 여럿("402든 156이든 먼저 오는 것")이면 `transit_options` 로 최대 3개를 저장한다 (`commute_rides`, order_no 0 이 기본이고 `station_ids`·`line` 은 그 거울). 계획마다 걷는 구간·샛길 후보를 F-03 에서 미리 만들어 두고, 카드는 전체 계획의 후보를 합쳐 고른다. 매일 어느 노선을 탔는지는 그중에서 고르면 되고 서버 호출이 늘지 않는다. 응답의 `rides[]` 와 경로의 `ride_id` 로 구분한다
- **테스트 기준** 저장한 좌표가 응답으로 돌아옴 · `transit`인데 정류장 없으면 400 · 모르는 정류장 400 · 두 번 저장해도 사용자당 1개 · 취향 기본값 `full`

### F-03 샛길 생성

- **입력** 출발·도착 좌표, 교통수단, 정류장 목록, 취향(`short`/`full`/`sunset`), 사용자 태그 가중치
- **처리**
  1. 교통수단별 **걷는 구간** 결정. `walk` → 전체 / `transit` → 앞 도보 · 뒤 도보 · 1~3 정거장 먼저 내리기 · 1~3 정거장 걸어가서 타기 / `car` → 도착 후 반경 10분. 탑승·하차역 자체는 건너뛰지 않는다. 건너뛸 정류장은 동선 저장 때 사용자 구간에서 정한다
     - 탑승 계획이 여러 개면 **계획마다** 위 구간을 만든다 (#88). 같은 좌표의 TMAP 요청(같은 승차 정류장까지의 앞 도보 등)은 한 번만 부른다. 추가 시간·녹지 증가의 기준선은 **같은 계획의** 구간이다
     - 건너뛰기 구간의 추가 시간 = 걷는 시간 − 원래 도보 구간 최단 − 정거장당 2분(덜 탄 시간). 녹지 증가도 원래 도보 구간 최단과 비교. 그냥 걷는 최단 경로 자체도 후보가 된다
     - 경유지 경로가 지나온 길을 100m 넘게 다시 밟으면(공원 안 왕복) 버린다 (#49)
     - **방향 (#56)**: 동선은 집(from) → 회사(to)로 저장하고 경로도 출근 방향 한 벌만 만든다. 걷는 길은 거꾸로 걸어도 같아서 퇴근으로 볼 때는 앞 도보↔뒤 도보, 먼저 내리기↔걸어가서 타기를 맞바꾸고 좌표·이름·정류장을 뒤집고 반대 방향 일몰 비율을 쓴다 (TMAP 추가 호출 없음). 도착 후 구간만 방향마다 따로 (출근 = 회사 주변, 퇴근 = 집 주변). 오늘 카드는 퇴근 방향, 경로 API 는 `direction=to_home|to_work` (기본 퇴근)
  2. 각 걷는 구간의 최단 보행 경로를 TMAP 보행자 API로 받는다 (기준선). 소요 시간 `baseMinutes`
  3. **경유지 추리기 (규칙)**
     - ① Place 테이블에서 기준선 600m 버퍼 안의 지점 (`ST_DWithin`)
       - 지점이 공원·숲·잔디 폴리곤 **안**에 있으면 경유 좌표를 폴리곤 가장자리(기준선 쪽 경계점)로 옮긴다 (#82). 공원 한가운데를 경유지로 주면 TMAP 이 들어갔다 같은 길로 나와 왕복 필터에 탈락하기 때문. 도착 후 구간(공원이 목적지)은 그대로
     - ② 직선 우회량 `dist(A,W) + dist(W,B) − dist(A,B)` ≤ 취향별 상한 (아래 표)
     - ③ 취향 `sunset`이면 type에 노을·전망·다리 포함 지점만
     - ④ 6개 초과면 우회량 적은 순 상위 6개
     - 하천 지점은 진입점·진출점 쌍이 하나의 후보. 쌍은 Place 테이블의 `pairId`로 미리 정해둔다
  4. 남은 경유지마다 TMAP 호출 (`passList`) → 후보 경로. 호출 수 ≤ 6
  5. F-04로 각 경로의 녹지 % · 이벤트 점수 계산
  6. **후보 조건**: `addMinutes` ≤ 취향별 상한 **그리고** 녹지 % ≥ 최단 녹지 % + 취향별 기준. 통과한 것만
  7. 점수 = 녹지 % × 1.0 + 이벤트 점수 × 1.0 + clamp(Σ(태그 가중치), −2, 2) × 10 − addMinutes × 1.5 → 상위 3개
  8. 후보 0개면 F-15로

| 취향 | 우회 상한 (분) | 직선 우회량 상한 | 녹지 기준 (+%p) | 추가 규칙 |
| --- | --- | --- | --- | --- |
| `short` 짧게 | 8 | 600m | 5 | — |
| `full` 제대로 | 15 | 1,000m | 10 | — |
| `sunset` 노을 | 15 | 1,000m | 5 | 노을·전망·다리 지점만, 노을 창 안이면 노을 이벤트 점수 ×2 |

- **출력** Route: name · tag · legType · minutes · addMinutes · greenPct · eventScore · score · highlights · polyline · spots · alightStationId · boardStationId · skipStops
  - **journey (#77)**: 그 경로를 골랐을 때의 출발 → 도착 전체 여정. 조각 `{kind: walk|ride|drive, role: usual|saetgil|after_arrival, polyline, minutes?, line?, from_name?, to_name?}` 의 순서 목록. 앞 조각의 끝 = 뒤 조각의 시작. 후보는 자기 걷는 조각만 `saetgil`, 나머지는 기준선·탑승(`usual`). 걸어가서 타기·먼저 내리기는 첫·마지막 탑승을 그 정류장까지로 줄인다. 탑승 조각은 저장된 정류장(탑승·중간·하차) 좌표를 잇는 선이라 실제 노선 모양과 다를 수 있다. 도착 후 후보는 평소 여정 뒤에 `after_arrival` 조각. 프론트는 journey 로 한 줄을 그리고 `saetgil` 만 강조한다
- **성능** 데모 동선은 F-02 저장 시 사전 계산. 신규 동선 10초 이내. 취향 칩으로 재계산 시 API 재호출 없이 캐시된 후보 경로에 6~7번만 다시 적용
- **예외** TMAP 실패 → EXTERNAL_API_FAILED, 기존 캐시가 있으면 그것을 반환
- **테스트 기준** 고정 폴리곤 5개로 ①~④가 6개 이하를 내는지 · `short`에서 addMinutes 9인 경로가 제외되는지 · `sunset`에서 노을 태그 없는 지점이 ③에서 빠지는지 · 하천 쌍이 하나로 세어지는지 · 후보 0개면 F-15 호출

### F-04 녹지 % + 이벤트 점수

- **녹지 %** 경로 폴리라인을 50m 구간으로 자르고(`ST_Subdivide` 또는 보간), 각 구간 중심에서 30m 안에 녹지 폴리곤(공원·숲·잔디·하천·가로수 열)이 있으면 1. 비율 × 100
- **이벤트 점수** (0~30)
  - 물가: 구간 중 하천 폴리곤 50m 안인 비율 × 10
  - 다리·전망: 경로가 `bridge=yes` 구간 또는 type 전망 지점 100m 안을 지나면 +10
  - 노을 방향: suncalc 일몰 방위각과 경로 진행 방향 차이 ≤ 30° 인 구간 비율 × 10 (**노을 창** = 일몰 ±30분 안이고 날씨 맑음일 때만. 창은 코드 상수 하나)
- **테스트 기준** 녹지 폴리곤 위를 지나는 100m 직선 → 100% · 폴리곤 없음 → 0% · 다리 구간 포함 → +10

### F-15 대체 로직

| 단계 | 조건 | 행동 유형 | 카드 예시 |
| --- | --- | --- | --- |
| 1 | 걷기·먼저 내리기·걸어가서 타기 구간에 후보 있음. 한 후보군에서 점수 경쟁, 행동 유형은 1위의 구간 | `detour` 돌아가기 / `alight_early` 먼저 내리기 / `board_late` 걸어가서 타기 | "12분 돌아가면 신천 노을" / "2정거장 먼저 수성구청역에서 내리면 +12분" |
| 2 | 없음 + 기준선에 이벤트 점수 ≥ 10 | `delay` 늦추기 / `glance` 고개 돌리기 | "6분 늦추면 다리 위 노을" / "지금 왼쪽, 억새" |
| 3 | 없음 + 집·회사 반경 10분 안에 후보 있음 | `after_arrival` 도착 후 | "퇴근 후 집 앞 공원 7분" |
| 4 | 그것도 없음 | `none` | "오늘 동선엔 자연이 없어요" + 주변 자연 |

- 1단계는 F-03 결과로 판정, 2단계는 F-04의 기준선 이벤트 점수, 3단계는 F-03을 반경 10분 루프로 한 번 더
- 11/6 변경 (#51): 이전에는 걷는 구간 후보가 하나라도 있으면 "한 정거장 먼저"(옛 2단계)를 보지 않아, 점수가 더 높은 먼저 내리기 경로가 숨겨졌다
- **테스트 기준** 걷기 후보 → 1 detour · 먼저 내리기만 → 1 alight_early · 먼저 내리기 점수가 더 높음 → 1 alight_early · 후보 없고 이벤트 12 → 2 · 도착 후만 → 3 · 전부 없음 → 4

### F-05 오늘 카드 (AI 선택)

- **입력** 후보 ≤3개 (각각 name · legType · addMinutes · greenPct · eventScore · score · highlights · 장소 한 줄 설명) · 대체 단계 · 퇴근 시각 · 일몰 시각 · 날씨 · 미세먼지 · 동선 위 계절 상태 · 사용자 태그 가중치 상위 2개 · 최근 3일 추천 경로 id
- **처리**
  1. 서버가 후보 ≤3개와 점수를 만든다 (F-03). 서버는 1위를 정하지 않는다
  2. 서버가 **행동 유형**을 후보마다 붙인다: F-15 단계 + (퇴근 시각 − 일몰 시각) 차이 ≤ 10분이면 `delay` 가능 표시
  3. LLM 호출 1회. 입력을 JSON으로 넘기고 아래 스키마의 JSON만 받는다. temperature 0
     ```
     { "choice": <후보 index>, "actionType": "detour|alight_early|board_late|delay|glance|after_arrival",
       "reasonTag": "sunset|river|park|trees|air|season", "text": "<2문장, 80자 이내>",
       "deviation": "<점수 1위와 다르면 한 줄 이유, 같으면 null>" }
     ```
  4. 프롬프트 규칙: 장소·시각·거리·정류장 이름은 입력값만 사용 · 최근 3일 추천한 경로는 피한다 · 점수 1위와 다르게 고르면 `deviation` 필수 · 이유는 하나만
  5. 검증: `choice`가 범위 밖이거나 `text`에 입력에 없는 장소명이 있으면 실패 처리
- **예외** LLM 실패 또는 검증 실패 → 점수 1위 + 템플릿 문장 ("{정류장}에서 내리면 +{분}분, {장소}") · reasonTag는 이벤트 최대 항목
- **출력** TodayCard. 데모는 퇴근 카드만 만든다 (출근 카드는 2차. 그때 period 컬럼을 추가한다)
- **데모 조건** "다른 길 보기"에서 AI 선택과 점수 1위가 다른 날이 1일 이상 보이도록 데모 데이터를 준비한다 (예: 노을 날에 녹지 2위를 고름)
- **테스트 기준** 스키마 밖 JSON → 템플릿으로 폴백 · 입력에 없는 장소명 → 폴백 · 정상 응답 → TodayCard 저장 · 같은 입력 두 번 → 같은 choice

### F-16 취향 · 피드백

- **취향 칩** 홈 카드 아래 3개. 누르면 F-03의 6~7번(후보 조건·점수)만 캐시된 경로에 재적용 → F-05 재호출 → 카드 갱신. 오늘만 적용, 기본 취향은 안 바뀜
- **피드백** 걷는 중 화면 도착 시 별점 1~5 (11/6 회의: 👍/👎 두 단계보다 세분화). 저장: Feedback(userId · routeId · date · rating · tags). 동선을 다시 저장해 경로가 새로 만들어져도 평가 기록은 남는다 (routeId 만 비움, 평가 당시 태그 보관)
- **가중치 갱신** 그 경로의 태그(river · park · trees · sunset · bridge) 각각 (별점 − 3) × 0.1 (5점 +0.2 · 4점 +0.1 · 3점 0 · 2점 −0.1 · 1점 −0.2). 같은 날 같은 경로를 다시 평가하면 차이만 반영. 범위 −1.0 ~ +1.0. User.tagWeights JSON에 저장. F-03 7번 점수에 Σ(태그 가중치)를 ±2 로 자르고 × 10 으로 반영
- **기본 취향 자동 제안** 같은 태그에 4점 이상 3회 누적 → 마이 › 취향 설정에 "요즘 하천길을 좋아하시네요" 표시. 기본 취향은 사용자가 바꿀 때만 바뀐다
- **발표 용어** "학습"이 아니라 "피드백 가중치", "개인화 규칙"
- **테스트 기준** 5점 → river +0.2 · 3점 → 변화 없음 · 1점 후 4점으로 고치면 +0.1 · 상한 1.0 초과 안 함 · 가중치 반영 후 점수 순서가 바뀌는 케이스 1개

### F-11 남기기 (비전 태그)

- **입력** 사진 1장 · 장소(Place id 또는 현재 위치 100m 안 Place 자동) · 한 줄(선택)
- **처리** 비전 API 1회. 프롬프트: 아래 두 값만 JSON으로
  - `season`: `cherry` 벚꽃 / `foliage` 단풍 / `ginkgo` 은행 / `snow` 눈 / `sunset` 노을 / `none`
  - `stage`: `peak` 절정 / `mid` 중간 / `end` 끝물 / `none`
  - 퍼센트는 출력하지 않는다
- **UI** 제안 태그를 선택 상태로 보여주고 사용자가 바꿀 수 있다 → 저장
- **예외** 비전 실패 → 태그 미선택 상태로 사용자 직접 선택
- **저장** Record(userId · placeId · date · season · stage · aiSeason · aiStage · title · image). 사진은 프론트가 Supabase Storage에 사용자 토큰으로 직접 올리고 서버는 경로만 저장한다. 위치 메타데이터 제거는 프론트가 업로드 전에(재인코딩)
- **테스트 기준** 비전 응답 스키마 밖 → 직접 선택으로 폴백 · 정상 → aiSeason 저장 · 사용자가 바꾸면 season ≠ aiSeason 저장

- "이 길로" 버튼. 턴바이턴 안내는 만들지 않고 "카카오맵으로 안내" 딥링크로 넘긴다

### F-07 지역 전환 (스트레치)

- 녹지 · 큐레이션 · 정류장 데이터를 `city` 파라미터로 분리. 11/7 이후 여유 시 서울 동선 1개(홍대입구→공덕, 경의선숲길)
- 여유 없으면 오프라인에서 1회 돌려 발표 자료에 스크린샷 1장

### F-17 자연어 취향 (⚠️ 시간 되면)

- **입력** 자유 텍스트 ("오늘 답답한데 짧게", "비 오니까 그냥 빨리")
- **처리** LLM 1회, 출력은 `{ "mode": "short|full|sunset", "maxMinutes": 5~20 }` JSON만. 그 값으로 F-03 6~7번 재적용. **AI가 경유지를 고르지 않는다** — 조건값만 정한다
- **예외** 파싱 실패 → 기본 취향 유지, 안내 문구
- **테스트 기준** "짧게" → short · "노을 보고 싶어" → sunset · 의미 없는 입력 → 기본 취향

## AI 구현 방식

- **LLM 호출은 두 곳** (F-05 선택·문장, F-17 의도) + **비전 호출 한 곳** (F-11). 전부 API 1회, 구조화된 JSON 입출력
- **임베딩 · 벡터 DB · RAG · 파인튜닝은 쓰지 않는다.** 큐레이션 지점 설명(30곳)은 DB에서 꺼내 프롬프트에 그대로 넣는다. 지점이 수천 개가 되기 전까지 검색이 필요 없다
- **"튜닝"은 두 종류뿐**: 규칙 조건값(버퍼 600m, 우회 1km, 가중치 별점당 0.1)은 코드의 상수 · LLM 출력 형식·말투는 프롬프트 문자열. 둘 다 코드 안에 있고 모델은 바꾸지 않는다
- **AI가 틀릴 수 없게 하는 장치**: 입력값만 사용 규칙 · JSON 스키마 검증 · 입력에 없는 장소명 검출 · 실패 시 규칙 기반 폴백
- **발표 한 줄**: "길은 지도가 찾고, 조건은 규칙이 거르고, 오늘의 선택과 이유는 AI가. AI는 숫자가 나온 뒤에만 개입합니다"

## 비기능 · 기술 스택

- 🔒 **개인정보** 출발·도착 좌표는 경로 계산에만 쓰고 본인 외에 공개하지 않는다 · 기록 사진은 업로드 전 위치 메타데이터 제거 · 기록은 나만 보기
- 👤 **계정** 이메일·비밀번호 가입 (Supabase Auth, 인증 메일 없음) · 둘러보기 · 심사용 데모 계정은 seed 스크립트로 생성해 제출 시 동봉
- 📱 **반응형** 모바일 하단 탭 4개
- ⚡ **성능** 데모 동선 사전 계산 · 신규 동선 10초 · 카드 5초 · 취향 칩 재계산 3초 (API 재호출 없음)
- 🌐 **배포** 외부 접속 URL
- 🤖 **AI** 추리기와 점수는 규칙, 선택과 설명은 AI. AI는 숫자가 나온 뒤에만 개입. 실패 시 규칙 폴백 · 키는 서버에만
- 🏙 **도시 분리** 녹지 · 큐레이션 · 정류장 데이터는 `city` 파라미터로. 코드에 "대구" 하드코딩 금지
- 🎬 **데모** 동선 3개 사전 검증 · 알림 잠금화면 목업으로 시작 · AI 선택 ≠ 점수 1위인 날 1개 포함 · 녹화 백업
